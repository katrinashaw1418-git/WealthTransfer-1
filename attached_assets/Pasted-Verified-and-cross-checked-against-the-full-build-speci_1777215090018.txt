What must be fixed — confirmed, plus precision corrections
Fix 1 — Version integrity not enforced (confirmed critical)
The review is correct. The spec says "version created on every write" but the current schema and API spec have no mechanism preventing a developer from writing directly to a plan table without the versioning wrapper. The fix is correct: wrap all plan writes in a writeWithVersioning service function and make it the only permitted write path. Direct ORM calls to plan tables must not be allowed outside that wrapper.
One precision correction here: the review suggests a DB trigger as "optional but strongly recommended." This should be rephrased as "strongly recommended as a belt-and-suspenders backstop, not a substitute for service-layer enforcement." Triggers are hard to test and can be bypassed by superuser connections. Service-layer enforcement is the primary control; the trigger is the fallback catch.
Fix 2 — Disclaimer gate missing version binding (confirmed critical)
The review is correct. The current spec ties the disclaimer acknowledgement to wealthPlanId but not to a specific plan version. A client who acknowledged version 3 of the disclaimer would pass the gate even after a material plan update creates version 8. The fix is correct: add wealthPlanVersionId to adviceDisclaimerAcknowledgements and make the gate check that the client has acknowledged the current version, not just any version.
One precision correction: the review says "bind acknowledgement to plan version." To be completely precise, there are two distinct version concepts in this system — the wealthPlanVersions row (which tracks plan state over time) and the disclaimerVersion text field (which tracks which disclaimer text was shown). The gate needs to check both: the client must have acknowledged (a) the current disclaimerVersion string and (b) a wealthPlanVersionId that matches or post-dates the last substantive plan change. If the plan is updated in a way that creates a new version, the prior disclaimer acknowledgement should be considered stale and require re-acknowledgement. Both fields are needed on the acknowledgement record.
Fix 3 — Plan lock during review (confirmed critical)
Correct. The status: under_review field exists but no enforcement logic blocks writes during that state. The fix is correct: when wealthPlan.status = under_review, the API must reject any POST to recommendations, objectives, or risk profile snapshots with a 423 Locked or 409 Conflict response and a clear error message. Only notes, compliance actions, and review resolution are permitted during a review.
Fix 4 — selectedModelPortfolio needs a validated shape (confirmed critical)
Correct. Raw jsonb with no shape contract will produce unreadable history within months. The ModelPortfolioSnapshot type definition in the review is the right shape. Add version to it (the review includes this) and validate against it on insert. Reject any POST to riskProfileSnapshots where selectedModelPortfolio does not conform to the expected shape.
Fix 5 — Recommendation must link to plan version (confirmed critical)
Correct. A recommendation linked only to a riskProfileSnapshotId but not to a wealthPlanVersionId means you cannot reconstruct the exact plan state that existed when a recommendation was made. This is the gap that matters most in a regulatory review — "what did you recommend, when, and in what context." The fix is correct: add wealthPlanVersionId to wealthPlanRecommendations.

What must also be fixed — the other five items
Fix 6 — Notes supersession field (confirmed)
Correct. Adding supersedesNoteId makes the audit chain traversable. This is not cosmetic. Without it, you have a chronological list of notes with no explicit chain of custody. The fix is to add the field. It is nullable (first note in any chain has no predecessor), but every note that is intended to supersede a prior note must set it.
Fix 7 — Admin write prohibition must be centralised (confirmed)
Correct. The current spec states the rule in prose but does not enforce it architecturally. A future developer adding an admin route has no code-level signal that writes are prohibited. The fix is to centralise write permission assertions: assertWriteRole(user, ["adviser"]) must be the only permitted path to any plan write. No exceptions.
Fix 8 — Soft delete prohibition (confirmed)
Correct. The spec never explicitly bans DELETE. Without a stated and enforced prohibition, a developer may add a delete route thinking it is helpful. The fix is to either revoke DELETE at the DB level on all planner tables, or enforce at the ORM/service layer that no delete operation is permitted. Explicit prohibition is better than hoping no one adds it.
Fix 9 — Audit log needs before/after state (confirmed)
Correct. Logging action and resourceId without before and after state is not regulator-grade. A regulator reviewing a complaint about a recommendation change needs to see exactly what changed, not just that a change occurred. The fix is correct: add metadata: { before: {...}, after: {...} } to every audit log write in the planner layer.
Fix 10 — Client acknowledgement of recommendation needs acknowledgedBy (confirmed)
Correct. The acknowledged_at timestamp without acknowledgedBy: integer(clientUserId) means you cannot prove which client clicked acknowledge, only that something was set. The fix is to add acknowledgedBy as a foreign key to users.id on wealthPlanRecommendations.

What should be added to future-proof — assessment
Addition 1 — Plan freeze endpoint (confirmed, add to Step 5)
POST /api/adviser/wealth-plans/:id/freeze creating a version snapshot and setting status = under_review is correct and should be added to the Step 5 API build. It is not optional — without it, the "plan lock during review" fix has no explicit trigger. A compliance_admin or admin must be able to call this endpoint.
Addition 2 — Compliance flag severity (confirmed, add to schema)
flagSeverity: low | medium | high | critical on the compliance flag record is correct. Without severity, all flags look equal and compliance triage becomes impossible. Add it.
Addition 3 — Recommendation risk alignment check (confirmed, add to Step 5 gates)
Before inserting a recommendation, the API must compare the recommendation's assetClassFocus and implied risk level against the client's current riskProfileSnapshot.riskTolerance. If the recommendation risk exceeds the client risk profile, block with a 400 and a clear error. This is the kind of check that, if missing, becomes a regulatory finding. Add it as a server-side gate in Step 5.
Addition 4 — No financial product reference guard (confirmed, add as soft filter)
Blocking wording like "buy", "allocate to", or specific fund names in recommendationText until AFSL/AR is in place is a reasonable guardrail. This should be implemented as a server-side content check that flags or rejects recommendations containing prohibited terminology. It does not need to be a hard block at this stage — a flag returned in the API response that requires the adviser to confirm is sufficient. Do not let this slip to "optional" — it is the last line of defence before a general advice record accidentally contains personal advice language.
